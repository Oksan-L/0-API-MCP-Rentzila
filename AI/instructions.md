# Copilot Instructions — Rentzila API Tests

## General
- All comments in code must be in English
- First line of every generated file must be: `// Generated by AI`
- After each generation, create or append a log entry to `/AI/logs.md` with:
  - date
  - short summary of what was done (1-2 sentences)
  - files created or modified

## Stack
- Playwright Test with TypeScript
- Base URL: https://dev.rentzila.com.ua
- API documentation: https://dev.rentzila.com.ua/api/docs/
- Auth: JWT Bearer token via POST /api/auth/jwt/create/
- Node.js with dotenv for environment variables

## Project Structure
- `api/endpoints/` — API client classes (one file per resource)
- `tests/<resource>/` — test spec files
- `helpers/auth-helper.ts` — getAuthToken() function
- `helpers/data-factory.ts` — test data factories
- `.env` — TEST_EMAIL, TEST_PASSWORD, BASE_URL

## Environment Variables
- Always use process.env for credentials — never hardcode login/password
- Auth token must be obtained via getAuthToken() from helpers/auth-helper.ts
- Example:
```typescript
  import { getAuthToken } from '../../helpers/auth-helper';
  const token = await getAuthToken(request);
```

## API Client Pattern
- Create a class in `api/endpoints/<resource>.ts`
- Constructor accepts `APIRequestContext`
- One method per endpoint
- Methods return raw `APIResponse` — no assertions inside client methods
- Pass auth token via Authorization header: `Bearer ${token}`
- Example:
```typescript
  async getCategories() {
    return this.request.get('/api/category/');
  }
```

## Test File Pattern
- File location: `tests/<resource>/<action>.spec.ts`
- First line: `// Generated by AI`
- Use `test.describe` with full endpoint path and tags as label
- Import structure:
```typescript
  import { test, expect } from '@playwright/test';
  import { ResourceAPI } from '../../api/endpoints/resource';
  import { getAuthToken } from '../../helpers/auth-helper';
```
- Use `test.describe.configure({ mode: 'serial' })` only when tests have dependencies between them
- Use `test.beforeAll` for token and shared setup
- Use `test.beforeEach` to instantiate API client

## Test Structure Order
1. Happy path (positive tests)
2. Validation errors (400)
3. Auth errors (401/403)
4. Not found (404)

## Tags
Add tags directly in test/describe name strings:
- `@smoke` — critical happy path tests
- `@auth` — auth-related tests
- `@units` — units resource tests
- `@category` — category resource tests
- `@me` — /me/ endpoint tests
- `@favourites` — favourites tests

## Assertions Checklist
For every endpoint cover:
1. Status code (exact)
2. Response body has required fields
3. Field types match schema
4. Auth errors — always test with empty token and invalid token

## Known API Behavior (DRF specifics)
- Unauthenticated requests return 403, not 401 (DRF default)
- Non-existent resources may return 500 instead of 404 — document with BUG comment
- Successful creation returns 201, not 200
- Successful update returns 202, not 200
- Comment any unexpected status code with: `// BUG: should return X, but API returns Y`

## Cleanup
- Always delete test data created during tests
- Use `test.afterAll` for cleanup of resources created in `test.beforeAll`
- Use inline cleanup after the action when using serial mode

## What NOT to do
- Do not hardcode credentials
- Do not add assertions inside API client methods
- Do not skip cleanup after creating test data
